# Kill-9 probe: does background work outlive its session? (2026-10-27)

Plan: `docs/superpowers/plans/2026-10-27-horizon-stage-a.md`, Task 1.

## Method

**Setup:**
- Run in the throwaway directory `/tmp/h-kill9`.
- Claude Code CLI with Haiku 5.5, allowed tools `Agent` and `Bash`.
- The session gets its own process group via `perl -e 'setpgrp; exec ...'`.

**Prompt:** dispatch a background Agent whose only job is a Bash loop. The loop appends a timestamp to `beat.txt` every 2 s, 60 times (about 120 s in total). The session then runs `sleep 120` itself.

**Measurement:** once `beat.txt` had lines, the probe waited 6 s, killed, counted the lines, waited 20 s and counted again.

**Two trials:**
- **A:** `kill -9` only the parent `claude` process.
- **B:** `kill -9 -- -PGID`, the whole process group. This is what the mini GPT study harness does at the call cap.

The user ran the probe. The auto-mode classifier blocked the controller's helper from launching it. Script: see the end of this file.

## Result

| Trial | Kill | Lines before | Lines 20 s later | Outcome |
|---|---|---|---|---|
| A | parent only | 4 | 14 | kept running |
| B | whole process group | 4 | 13 | kept running |

The probe's cleanup (`pkill -f h-kill9/beat.txt`) stopped the loop afterwards, and no processes were left.

## Conclusion

**The agent dies with the session, but a shell command it started does not.**
- The subagent's reasoning lives inside the `claude` process, so it stops.
- The Bash command it had already launched kept writing for the rest of its run, even after the whole process group was killed. That means Claude Code runs tool commands outside the session's process group.

**What this means for Horizon:**
- **Leases are still the right way to free the ledger.** Nothing will report the death, so expiry is the only signal. This matches the spec, Principle 3.
- **A reclaimed attempt may still have a command writing to the workspace,** such as a test run, a training job or a build. A reclaim cannot stop it: the CLI never holds those PIDs, and hooks don't receive them.
- **No false completion follows.** Completion re-checks the tree hash, so a late write invalidates an earlier pass instead of slipping through, as Stage A A1 notes. But a resumed session can see files change under it until the orphaned command ends.
- **The spec's fallback applies:**
  - Option B's per-attempt worktree isolation would contain these writes.
  - A cheaper partial step is to tell workers to bound long commands with a timeout.
  - The tree-hash re-check already makes any interleaving visible.
- **Study confound:** in the mini GPT cap study, a session killed at the call cap could leave a running command (for example, training) that continued into the next session. Every arm alike is exposed to this.

## Script

```bash
DIR=/tmp/h-kill9
mkdir -p "$DIR" && cd "$DIR" || exit 1
PROMPT='Use the Agent tool with run_in_background set to true. The agent must run exactly this Bash command and nothing else: for i in $(seq 1 60); do date +%s >> /tmp/h-kill9/beat.txt; sleep 2; done. After dispatching it, run this Bash command yourself: sleep 120'
trial() {
  local name=$1 mode=$2
  rm -f beat.txt
  perl -e 'setpgrp; exec @ARGV' claude -p "$PROMPT" --model claude-haiku-5-5 \
    --allowedTools=Agent,Bash > "claude-$name.log" 2>&1 < /dev/null &
  local pid=$!
  local waited=0
  until [ -s beat.txt ] || [ $waited -ge 180 ]; do sleep 1; waited=$((waited + 1)); done
  [ -s beat.txt ] || { echo "trial $name: worker never started"; kill -9 -- -"$pid"; return; }
  sleep 6
  if [ "$mode" = parent ]; then kill -9 "$pid"; else kill -9 -- -"$pid"; fi
  local before after
  before=$(wc -l < beat.txt); sleep 20; after=$(wc -l < beat.txt)
  echo "trial $name ($mode kill): before=$before after=$after"
}
trial A parent
trial B group
pkill -f "h-kill9/beat.txt"
```
